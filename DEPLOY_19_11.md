# SkinCar · сервер GitHub → Railway, накопительная сборка 19.11.2026

**Состав:** полный сервер из предоставленного `skincar-server-main 19.11.zip` + накопительный Railway-патч SK-008 (включая SK-023, SK-082, SK-084, SK-080, SK-078) + исправление противоречивых инструкций для ГРНЗ. Это НЕ только патч.

## Перед публикацией
1. Сделайте snapshot / backup PostgreSQL и сохраните SHA текущего коммита GitHub; проверьте, нет ли более новых коммитов после экспорта от 19 ноября. Если появились — сначала сравните и объедините, не перезаписывайте их слепо.
2. Проверьте, что Railway использует правильный репозиторий, ветку и root directory; не удаляйте сервис и существующую БД.
3. Убедитесь, что все секреты (BOT_TOKEN, DATABASE_URL, WEBHOOK_SECRET, OPENAI_API_KEY) находятся **только** в переменных Railway, не в GitHub. Не публикуйте значения секретов или резервные копии БД.
4. Подтвердите разрешения на изображения перед публичным доступом к каталогу дисков. Плёнки начинают с пустого каталога.

## Обновление GitHub
- Распакуйте `SkinCar_19-11_GITHUB_RAILWAY_FULL.zip` в локальную копию репозитория сервера и замените/добавьте одноимённые файлы. Не загружайте архив ZIP внутрь репозитория как файл, если Railway ожидает исходники.
- Не копируйте `node_modules`, `.env` и временные `wheel-references` (они генерируются при старте из проверенного `wheel-references.tar.gz`).
- Сохраните существующую git-историю, сделайте commit, и только затем отправьте изменения в ветку, которую отслеживает Railway.
- Минимум Node.js 22; `npm ci`, `npm start`. Стартовая команда распаковывает проверенные 107 серверных референсов, затем запускает `server.js`.

## База данных
- `server.js` при запуске выполняет `schema.sql`. В этой версии миграция добавляет `generations.charged_credits INTEGER NOT NULL DEFAULT 1 CHECK (charged_credits BETWEEN 1 AND 100)`; существующие записи считают ранее оплаченной одной генерацией.
- SK-008 добавляет JSONB-параметры (плёнка/SKU/зона) и отдельные файлы, новых таблиц для плёнок нет. Нет `DROP TABLE`, `TRUNCATE` и намеренного удаления данных в SQL-схеме.
- Перед запуском на реальной БД всё равно нужен **backup**; никакой локальный тест не эквивалентен миграции на рабочем PostgreSQL.

## После деплоя Railway, до Netlify
1. Подтвердить успешный деплой и доступность `/health`.
2. Проверить авторизованный профиль, существующие автомобили и черновики; проверить, что баланс не изменился от одного перезапуска.
3. Проверить создание заданий Standard=1 кредит / HD=3 кредита, корректный возврат списанного при ошибке, отсутствие двойного списания при повторе запроса.
4. Проверить SK-080: исключение из **дневного** лимита задано только нужному Telegram ID; не ослаблять лимит одной активной задачи и проверку баланса.
5. Для первого QA безопаснее оставить коммерческие оплаты выключенными или тестовыми (`PAYMENTS_MODE=off`/`pilot` согласно текущей инфраструктуре); не включать `live` без отдельного решения.

## Netlify
Только после успешного деплоя Railway загрузить `SkinCar_19-11_NETLIFY_DEPLOY.zip` в **тот же сайт** Netlify, не создавать новый без необходимости. В архиве корень: `index.html`, `cars/catalog.json`, `wheel-packs/`, `film-packs/index.json`. Открыть Telegram Mini App заново и пройти мобильный чек-лист в мастер-архиве.

## Плёнки
Новый каталог изначально пуст. Нельзя разрешать выдуманные материалы и платные вызовы. Для реальных моделей нужны подтверждённые SKU, локальные референсы в обоих окружениях и явный whitelist `FILM_APPROVED_SKUS` на Railway. Перед массовым импортом согласовать значения Excel-шаблона с контрактом сервера. Документ: `FILM_TEMPLATE_MAPPING_19_11.md` внутри мастер-архива.

## Что НЕ проверено в архиве
Рабочая PostgreSQL, реальные оплаты Stars, внешние запросы к модели и полноценная работа внутри Telegram на iPhone. Интеграционные тесты с PGlite требуют установки npm-пакетов из `package-lock.json`. Запуск в production сделает пользователь после проверки и резервного копирования.
